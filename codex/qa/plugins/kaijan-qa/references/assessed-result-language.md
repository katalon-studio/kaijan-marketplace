# Present assessed results

Use the separate, validated assessment of the selected test and run for the final user result. Lead with what happened in the application. For example: “The copy kept its changed name after reload. The original kept its original name.” Use the actual names and observations, not this example as evidence.

Keep Runner's original verdict, attribution and evidence unchanged in the records. Preserving them does not require repeating them in chat. After a valid linked assessment passes or fails, do not append “Runner remains unverified,” authentication disclaimers, or an explanation of the assessment pipeline. This is not a second failure beside the assessed result.

When assessment is absent, invalid or inconclusive, report only supported observations. Do not convert completion into a pass, hide an observed failure, or claim that the full request passed. State a concrete execution blocker when it prevents the requested work or needs user action. Omit generic missing-check commentary and claims about unrelated environments.

Use short active sentences for manual QA testers who do not know our internal terms. Keep proprietary Kaijan engine diagnostics in internal records. A customer request does not authorize their disclosure. Follow the [shared confidentiality rule](local-capabilities.md#presentation), including for technical questions. Explain customer-owned app facts, requirements, results, evidence and useful recovery steps without exposing engine details. Preserve original source IDs and immutable evidence internally; do not strip or rewrite them to make a report look better.
